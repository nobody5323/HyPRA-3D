# 预设 AI 适配（导入社区预设后一键改造）

> 定位：`docs/st-preset-compat.md`（酒馆预设兼容契约）的**配套功能**。
> 兼容层让社区预设「能跑」，适配层让它「跑得像本项目的陪伴对话」。

## 0. 一句话范围

用户导入酒馆预设后，点一次「AI 适配」：先给出**建议**（改了哪些条目、哪个字段、
从什么变成什么），用户确认后才写入覆盖层。原始导入文件始终只读，随时可回滚。

## 1. 要解决的问题

社区预设多数是**第三人称小说续写台**（面向创作型模型），与 HyPRA 的
「一对一陪伴对话」形态有系统性差异。实测一份典型预设（启用 28 条 / 3846 字）
暴露的问题：

| 症状 | 成因（结构性） |
|---|---|
| 人称不对 | 条目强制「全程第三人称」，把用户当作被叙述的角色 |
| 格式污染 | 要求输出正文标签、思考标签、按固定模板排版；含面向特定模型的特殊 token |
| 回复慢 | 要求单次正文 ≥2500 字；开启推理模式；回复长度上限给到 32000 |
| 角色感弱 | 把 AI 定位为「与用户合作的创作者」而非角色本人 → 模型没有理由调用情绪工具，触发兜底补逻辑再补一次调用 |

这些问题**不是代码缺陷**，是预设内容与项目形态不匹配；因此解法是改造内容，
而不是在渲染层打补丁。

## 2. 数据流

```
导入的预设（原文件只读）
   ↓
① 规则层  detect()      确定性体检 + 确定性修复        ← 不调用模型
   ↓ 产出：问题清单 / auto_patch / 待改写清单 / 保护清单
② 规划层  plan()        一次模型调用改写条目正文        ← 只调用一次
   ↓ 产出：最终覆盖层补丁（规则层 ⊕ 模型）
③ 前端确认  展示前后对照（diff），用户点「应用」才落盘
   ↓ 应用 = 把②那份补丁原样写入（PATCH /chat/st-presets/{id}）
覆盖层（st_compat.store.patch_override）
```

**为什么「应用」不重跑适配**：重跑会有第二次模型输出（温度非零，结果可能不同），
落盘的就不是用户在对照里看到的那份内容了。「模型只调用一次」也因此是真正的
一次：整个流程里 `llm.chat()` 只发生在②。

## 3. 为什么分两层

一份预设动辄上百条、正文上万字，全交模型既贵又容易漏。而「阈值超标」
「宏里写了标签」「字数要求过大」是**确定性判断**，不该占用模型调用。

实测这份预设里，慢与格式两类问题全部落在规则层（零 token），只有人称、
身份定位、特殊 token 三类需要语义理解才交模型——4 个条目、一次调用。

## 4. 规则层

规则写在 `backend/app/prompts/adaptation/rules.yaml`，改规则不用动代码。

### 4.1 处置动作

| action | 含义 |
|---|---|
| `auto_patch` | 规则层直接生成覆盖层补丁（确定性，不消耗模型调用） |
| `llm_rewrite` | 需要模型语义改写条目正文 |
| `preserve` | 内容与开关都不动，只建议调整注入位置（NSFW / 破限类） |
| `review` | 只提示，交用户决定 |

### 4.2 修法（`fix`）

仅 `auto_patch` 使用，由 `detector.py` 按标识分发：

| fix | 行为 |
|---|---|
| `disable_thinking` | 关闭推理模式（写入 `assembly.show_thoughts=false`） |
| `clamp_int` | 把预设字段的数值钳到 `target` 里的上限 |
| `disable_entry` | 关闭命中条目 |
| `clear_thinking_macro` | 把宏变量里的思考标签清空（只动标签片段） |
| `clamp_reply_length` | 把**已有的上限**（「不超过 N 字」）里的 N 换成 `target.reply_length` |
| `flip_reply_length_bound` | 把「不少于 N 字」这类**下限**翻转为「不超过 M 字」 |

### 4.3 适配目标（`target`）

`rules.yaml` 顶部的 `target` 段：人称口径、**输出形态**（`dialogue_only`）、
回复字数、推理开关、长度上限、总量预算。既用于生成模型提示词，
也作为确定性修复的目标值。

`dialogue_only: true` 是主导项——小说预设会要求写动作/环境/心理描写，
不说清楚的话，模型会把「以可见行动结尾」这类要求原样保留。

### 4.4 两类容易踩的坑（实测踩过）

**字数要求的方向常常是反的。** 小说预设写「不少于 2500 字」，在陪伴对话里
方向是反的。只把数字改小、保留「不少于」这个**下限**没有用：实测把 2500 钳到 300 后，
模型照样写 240 字；翻转为「不超过 100」后降到 24~47 字。

**纯排版规则用停用，不要交模型改写。** 「对白单独成段」「动作神态可穿插」这类
条目的价值就只是排版，交模型改实测会被敷衍（回一句「动作、神态可以穿插」），
反被复查判为残留而保留了旧内容。直接停用更可靠。

### 4.5 保护优先级（用户明确要求）

命中 `preserve`（NSFW / 破限）的条目：

- **不进入模型改写清单**，内容原样保留；
- **开关也不动**：即使它同时命中「整条即模板」这类本会触发停用的规则，
  也只告警、不停用（契约是「内容与开关都不动」）；
- 但两件事照做：确定性格式清理（只动标签片段，不触碰创作语义）、
  位置归拢（移到同语义槽位之后，只动顺序）。

槽位不存在时不写顺序补丁——宁可不移动，也不猜位置。锚点自身也被移动时
（两类保护互为锚点，如破限条目正文里带了 NSFW 关键词），用**多轮归位**处理：
既不报错，也不把条目从顺序里丢掉。

## 5. 规划层

`planner.py` 把待改写条目攒成**一个**提示词，调用一次 `llm.chat()`。

安全阀（宁可不做，不可做坏）：

| 风险 | 处置 |
|---|---|
| 模型返回非 JSON | 整批放弃，只保留规则层补丁 |
| 幻觉出新条目 | 只接受本次请求过的 `identifier`（marker 条目不在请求里，天然改不到） |
| 返回空内容 / 原文照抄 | 拒绝该条，保持原文 |
| 改写后**仍含**当初判定的问题 | 拒绝该条并说明原因——但不把**否定句**算作残留（见下） |

**否定句不算残留。** 模型常把条目改成「**不得**使用第三人称」「**不要**写动作、神态」——
关键词还在，但那恰恰是我们要的写法。只看关键词会让这两条改写被误拒，
旧内容（要求第三人称）保留，回复反而退回小说格式。实现上判断命中位置**之前**
一小段内是否有否定词（中文的否定几乎都是前置的）。
| 改写幅度过大 | **采纳但标注**「改动幅度较大，建议重点检查」——一刀切拒绝会卡住「删掉伪对话外壳」这类正当改动 |
| 模型调用失败 / 未配置模型 | 降级为「只应用确定性修复」，不抛异常 |

## 6. 接口

```
POST /chat/st-presets/{preset_id}/ai-adapt     # 出适配建议（默认不落盘）
{
  "dry_run": true,      // 默认 true：只返回建议，不写覆盖层
  "use_model": true     // false = 只做确定性修复，完全不调用模型
}
```

响应要点：`summary`（严重度计数）、`findings`（体检发现）、`preserved`（内容保留项）、
`rewrites`（逐条改写处置）、`diff`（前后对照，供界面直接渲染）、`patch`（可应用的补丁）、
`warnings`。`applied=true` 时额外返回 `detail`（最新预设详情）。

界面上的落盘走**现有的** PATCH 端点，而不是把 `dry_run` 改成 false 再跑一遍：
前者写入的正是用户确认过的那份 `patch`（见 §2 的说明）；后者保留给脚本 / 其他客户端使用。

适配结果写入的是**覆盖层**（`{preset_id}.override.json`），不是原始文件——
因此「恢复导入时」永远可用。

## 7. 合规边界（AGENTS.md §6）

- `rules.yaml` 只描述**判定规则**（正则与关键词为通用表述），不含任何
  SillyTavern 或社区预设的提示词正文；
- 预设正文与适配结果始终是**用户本地数据**，存于 `ST_PRESETS_DIR`
  （默认 `backend/data/presets`，已被 `.gitignore` 覆盖），不进仓库、不随发行物分发；
- 适配产出的 `patch` / `diff` 只在用户自己的浏览器与本地后端之间流转。
