# 插件市场设计（Plugin Market）

> 本文件是 `AGENTS.md §9.9` 的落地设计。**状态：设计稿，尚未实现**（远期项）。
> 实现前请先读 §9.3 的统一契约与 §6 的合规红线——市场不引入新契约，只补「从哪拿插件」这一段。

## 1. 定位：只做索引与安装机制

市场**不托管第三方代码**，只做两件事：

1. **索引**：告诉用户「有哪些插件、谁做的、什么许可、从哪下载」；
2. **安装**：把用户选定的插件包取回、校验、落到 `data/plugins/<id>/`，并支持回滚。

这条边界不是保守，是合规要求：`AGENTS.md §6` 明确「参赛提交物内不含任何第三方插件」，
而一旦开始托管代码，本项目就从「提供插件机制的宿主」变成「第三方代码的分发者」，
许可责任、内容责任、可用性责任全部随之而来——而这些都与一个参赛项目要证明的东西无关。

**参赛版本的市场长这样**：机制完整可用，索引指向自研示例插件（或为空）。
这样评审能验证机制，而仓库里没有一行第三方插件代码。

## 2. 与现有插件体系的关系

**不引入新的插件契约**。市场的产出物就是 §9.3 已有的东西：

```
索引条目 ──(下载+校验)──▶ data/plugins/<id>/manifest.json + 入口文件
                                    │
                            既有通路：discover() → setup() → start()
```

`PluginManifest` 的 12 个字段（`backend/app/plugins/manifest.py`）就是市场的元信息载体，
市场**不加字段**。理由：加字段意味着「只有市场装的插件才有某个字段」，
既有的目录插件（`tavern-bridge`、`live2d-model-source`）就会变成二等公民。

已经就绪、市场可以直接复用的部分：

| 能力 | 位置 | 备注 |
| --- | --- | --- |
| manifest 载入与校验 | `manifest.load_manifest()` | 含 id 规范校验、权限自相矛盾检查 |
| 目录发现（只读 manifest，不执行代码） | `manager.discover()` | 安装后重扫即可生效 |
| 权限强制 | `PluginContext._resolve_allowed()` | `write=false` 的插件拿不到写句柄 |
| 启停与落盘 | `manager.set_enabled()` / `data/plugins/<id>/state.json` | 重启保持 |
| 配置声明式 UI | `manifest.settings_schema` + `SchemaForm.tsx` | 市场不需要给插件写界面 |
| 管理接口 | `/plugins/*`（列表 / 启停 / 配置） | 市场只需再加安装相关端点 |

## 3. 数据模型

借鉴 Alife 的 `Plugin` / `PluginRelease` / `VersionResolver`，但落到 Python 数据类即可：

```python
@dataclass
class PluginRelease:
    version: str          # 语义化版本
    download: str         # https 直链（zip）
    sha256: str           # 完整性校验：防传输损坏，**不是**签名
    min_host: str = ""    # 要求的最低宿主版本（留空 = 不限）
    changelog: str = ""

@dataclass
class PluginListing:
    id: str               # 必须与插件 manifest 的 id 一致
    display_name: str
    summary: str
    author: str
    license: str          # SPDX 标识；空值视为「未声明」，界面须显著提示
    homepage: str
    releases: list[PluginRelease]
```

**索引格式**（`version` 用于将来结构变更时做兼容分支，与模型清单同构）：

```json
{
  "version": 1,
  "plugins": [
    {
      "id": "demo-datasource",
      "display_name": "演示数据源",
      "summary": "一句话说明它做什么",
      "author": "nobody5323",
      "license": "AGPL-3.0-only",
      "homepage": "https://github.com/nobody5323/HyPra-demo-plugin",
      "releases": [
        {
          "version": "1.0.0",
          "download": "https://example.invalid/demo-datasource-1.0.0.zip",
          "sha256": "（64 位十六进制）",
          "min_host": "0.1.0",
          "changelog": "首个版本"
        }
      ]
    }
  ]
}
```

索引来源（配置项，与 `LIVE2D_MANIFEST_PATH` 同思路）：

| 配置 | 说明 |
| --- | --- |
| `PLUGIN_INDEX_PATH` | 本地 JSON 索引路径（也接受 `file://`） |
| `PLUGIN_INDEX_URL` | 远程索引 URL（**仅 https**，需显式配置才启用） |

默认**两者都为空** → 市场界面显示「未配置索引」并给指路文案，与模型来源面板的处理一致
（`frontend/components/avatar/ModelSourcePanel.tsx` 是可直接照搬的样式）。

## 4. 安装流程：先出计划，再执行

安装的每一步都会产生用户需要知道的信息，因此**不能一键直达**。借鉴 Alife 的
「安装计划 + 回滚」：

```
① 解析      选定 listing + release → 校验 id 与版本合法性、宿主版本是否满足
② 下载      取回 zip（见 §5 的网络防护），校验 sha256
③ 预检      解压到临时目录 → 载入 manifest → 比对 id 是否与索引一致
            → 汇总「它将申请的权限」交给用户确认
④ 确认      界面展示：读写路径、网络白名单、贡献的能力面、是否可禁用
⑤ 落盘      备份现有同名目录（如有）→ 移入 data/plugins/<id>/
⑥ 生效      manager.discover() 重新扫描目录（不执行插件的 build）
            → 插件按 manifest 的 enabled 进入待启用状态
⑦ 失败回滚  任一步失败 → 删掉临时目录；已落盘则恢复备份目录
```

第 ③④ 步是整个流程里**唯一不能省**的：安装 = 引入可执行代码，
用户必须在代码落盘前看到它声明要碰哪些路径。这与 §9.3「权限是架构约束」是同一件事的两面
——宿主负责**强制**，界面负责**让人知情**。

第 ⑥ 步刻意**不调 `setup()`**：安装与启用是两件事。用户刚装完就看到一个
自动跑起来的第三方插件，比多一次点击糟糕得多。

### 4.1 升级与回滚

- 版本比较用语义化版本（三段数字），**不做** range / `^` / `~` 解析——插件生态没大到需要它；
- 升级 = 同一条流程，第 ⑤ 步把旧目录改名保留（`<id>.bak-<version>`），成功后删除；
- 失败则恢复旧目录，并把失败原因回给界面；
- **降级**同样支持（列表里可选任一 release），但要在界面上标明「降级」。

### 4.2 卸载

- 删除 `data/plugins/<id>/` 目录；
- `data/plugins/<id>/settings.json` 与 `state.json` **不自动删**——它们是用户数据，
  与插件代码分开存放正是为了这一刻（§9.3 的「配置与插件代码分离」）；
- 界面提供「同时删除配置」的勾选项，默认**不勾**。

## 5. 安全边界

市场的每一步都涉及「从外部取回代码并执行」，因此放弃含糊表述，逐条写清防线与**防线的极限**。

### 5.1 下载

| 防线 | 说明 |
| --- | --- |
| 仅 https | 拒绝 `http://`（明文可被中间人替换） |
| 拒绝内网地址 | `127.0.0.0/8`、`10/8`、`172.16/12`、`192.168/16`、`169.254/16`、`::1`、`fc00::/7` 一律拒绝——否则用户点一个索引条目就能让**服务端**去请求内网服务（SSRF） |
| 重定向 | 最多 3 跳，且每一跳都重新校验协议与地址 |
| 大小上限 | 解压前 20 MB、解压后 100 MB（防 zip 炸弹，与模型库的 `MAX_ARCHIVE_BYTES` 取同一量级） |
| 超时 | 连接 10s、整体 60s |
| sha256 | 索引必须给，校验不过直接中止 |

**sha256 不是签名**，这一点必须写在界面上：它能防传输损坏与镜像被替换，
**不能**防「索引作者本身就是恶意的」。安全感不能给错。

### 5.2 解压

复用 `backend/app/digital_human/model_store.py` 已有的两道防护（不重新发明）：

- `safe_relative_path()`：拒绝盘符、反斜杠、百分号转义、`..` / `.` 路径段；
- `_guard_inside()`：`resolve()` 之后再判是否仍在根目录内——符号链接也拦得住。

另加：拒绝绝对路径条目、拒绝指向目录外的符号链接、只接受普通文件与目录
（不处理设备文件等 zip 里可能出现的东西）。

### 5.3 信赖边界（写清楚，不留暗示）

- 插件是**任意代码执行**：安装后它跑在宿主进程里（除 `third-party` 层的显式例外外，
  本项目不做进程隔离）；
- 市场提供的是**来源透明**（作者、许可、直链、校验和），**不是安全担保**；
- `AGENTS.md §9.7` 已明确不做签名与沙箱。**不做的代价要写在界面上**：
  安装第三方插件 = 信任它的作者，与手动 `pip install` 一个包是同一性质的风险。
- 界面上必须避免「官方认证」「安全插件」之类的措辞——那是在暗示一个不存在的担保。

### 5.4 插件一律是「用户自己写的代码」——宿主不生成

早先版本有一项「AI 编写插件」（`/plugins/ai-draft` + `/plugins/install`），已**移除**
（`AGENTS.md §9.11` P11）。理由不是它技术上做不到，而是它把唯一真正的防线挤掉了：

- 生成的是**会被宿主 import 并执行**的 Python 源码，与安装第三方插件是同一类风险，
  不因「是本机模型写的」而更可信；
- 那时能靠的防线只有「默认禁用 + 用户先看代码」，但「一句话需求 → 一屏代码 → 点安装」
  这条动线本身就在鼓励用户跳过审阅——而这正是全部防线里唯一有效的那一环；
- 宿主只做得了语法层面检查（`ast.parse`）与回读校验，做不了语义安全判断，
  所谓「检查过了」反而会给人错误的安全感。

因此插件的来源收敛为一件事：**用户自己写**（接口见
[`docs/plugin-development.md`](plugin-development.md)，示例见
[`docs/examples/plugin-hello/`](examples/plugin-hello/)）。宿主只负责：

- **加载与强制**：`discover → setup → start → shutdown`，权限声明由 `PluginContext` 强制；
- **搬运**：`POST /plugins/import`（复制进用户目录，校验后落盘、失败回滚）
  与 `PLUGIN_EXTRA_DIRS`（零拷贝，宿主直接扫用户的开发目录）；
- **知情**：能力中心里看得见状态、错误原因与它声明的权限。

这与市场的关系：市场将来装的插件与手写插件走**同一条通路**（`data/plugins/<id>/` +
既有的 discover），所以 §5.3 的信赖边界对两者一字不差地适用——**来源透明，不是安全担保**。

## 6. 合规（§6 的落地）

| 要求 | 市场侧的动作 |
| --- | --- |
| 不托管第三方代码 | 索引只存**直链**，不存内容、不做镜像 |
| 许可可追溯 | 索引条目必须有 `license`（SPDX）；空值在界面上标为「未声明许可」并给出警示色 |
| AGPL 兼容性提示 | 安装前提示：**进程内耦合的插件视为衍生作品，须以 AGPL 兼容协议授权**（§6 的插件许可边界）；进程外/隔离边界的插件可自选协议 |
| 来源留痕 | 安装记录写 `data/plugins/<id>/install.json`：索引地址、release 版本、sha256、安装时间。卸载时保留，供事后审计 |
| 参赛物不含第三方插件 | 参赛版本的索引指向自研示例插件或为空；**CI 校验** `data/plugins/` 未被跟踪 |

最后一条建议做成 CI 检查项（与既有的「忽略目录不得有被跟踪文件」同类）：
`backend/data/` 已在 `.gitignore` 内，插件装在 `data/plugins/` 下天然不入库，
但仍应显式断言，防止将来有人把它挪到 `backend/plugins/`（那是随项目分发的位置）。

## 7. 依赖怎么办

**v1 不自动安装依赖。**

插件的 manifest 可以加一个**仅供展示**的字段：

```json
"requirements": ["httpx>=0.27", "beautifulsoup4"]
```

界面把它渲染成「此插件需要先自行安装：」+ 一行可复制的 `pip install httpx beautifulsoup4`。
用户装完插件后，`setup()` 若因缺依赖失败，§9.3 的失败隔离会把插件标成 `FAILED` 并记原因，
界面上能看到——这个回路已经存在，不需要市场额外做什么。

**为什么不做自动安装**：自动 `pip install` 等于让宿主任意执行第三方包，
比装插件本身风险更高（插件至少还有 manifest 和权限声明这一层可见性）；
而 Alife 那种 Pip/NuGet installer 需要锁文件、虚拟环境隔离、冲突解析一整套东西，
不属于参赛项目该背的复杂度。

## 8. 界面

市场挂在既有的能力中心里（`frontend/components/settings/`），不新开页面：

| 区块 | 内容 |
| --- | --- |
| 已安装 | 复用现有 `PluginCenter`（分层 / 状态 / 启停 / 配置表单） |
| 可安装 | 索引里的条目：名称、作者、许可、简介、可选版本 |
| 安装确认 | 一枚模态：权限清单（读写路径 / 网络白名单）、能力面、许可与信赖提示、sha256 前 8 位 |
| 安装记录 | 每行的「详情」里显示来源索引地址与安装时间（§6 的来源留痕） |

## 9. 实施顺序

| 阶段 | 内容 | 依赖 |
| --- | --- | --- |
| **M1** | 索引解析 + 列表展示（只读，不安装） | 无 |
| **M2** | 下载 + 校验 + 预检（到「确认」为止，不落盘） | M1 |
| **M3** | 落盘 + 重扫生效 + 失败回滚 | M2 |
| **M4** | 升级 / 降级 / 卸载 | M3 |
| **M5** | 索引远端获取（`PLUGIN_INDEX_URL`） | M1，需单独评审网络防护（§5.1） |

M1–M3 是「可用」的最小集合；M5 单独评审的理由是它把**读索引**也变成网络行为，
而 §5.1 那一整套防护必须同时覆盖它——与 P6 模型来源的取舍一致（那边干脆没做网络）。

## 10. 明确不做

| 项 | 理由 |
| --- | --- |
| 托管第三方代码 / 镜像 | §6 红线；本项目只给直链 |
| 自动更新 | 用户装了什么版本应该是用户的选择；自动更新等于让作者单方面替换已装代码 |
| 签名与信任根 | 需要密钥分发与信任根体系，本地可信边界（§6）下没有实际收益 |
| 依赖自动安装 | §7 |
| 评分 / 下载量 / 评论 | 需要服务端，与「静态索引」的定位冲突 |
| 沙箱执行 | §9.7 已否决；C 档 JS 沙箱也处于搁置状态 |
| 依赖解析（range / `^` / `~`） | §4.1；插件间的版本约束生态尚不存在 |

## 11. 与既有决策的一致性检查

- §9.2 的分层（`core` / `builtin` / `third-party`）：市场只装 `third-party` 层，
  并且**安装的 manifest 若声明为 `core` 或 `builtin`，一律拒绝安装**——
  那两个层只能随项目分发，否则「核心不可禁用」这条约束可以被一次安装绕过；
- §9.3 的契约：不新增字段、不新增生命周期钩子；
- §9.5 的声明式 UI：市场的安装确认界面由**宿主**渲染，插件不提供任何界面代码；
- §9.7 的「不做」：热重载不做（安装后重扫是显式动作，与 `/skills/reload` 同理）、
  插件自带 React UI 不做、沙箱不做；
- §9.11 P7：本文件即该阶段的设计产出，实现排在 P8 之后（或不做）。
