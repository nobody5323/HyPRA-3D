# 多模态感知与主动沟通能力设计

> 参照对象：[`liwusen/FaustBot-llm-vtuber`](https://github.com/liwusen/FaustBot-llm-vtuber)（GPLv3）
> 定位：HyPRA 从「你问我答」升级为「**看得见你、会自己开口**」。
> 状态：**已实现**（P1–P5，见 §7 与 §8.3）。关键选型已定（§8.1）。
> 参照项目只取**机制思想**，代码若复用须按 §6 登记。

## 0. 一句话结论

HyPRA 的**输出侧多模态已经完备**——情绪 → SSML → KA 动作 → 渲染无关驱动时间轴，
三条路径（魔珐 / 服务端 TTS / 静默）都能跑通。

真正缺的不是「再做一个数字人功能」，而是两条**新链路**：

| 链路 | 补什么 | 状态 |
| --- | --- | --- |
| **感知链路**（输入多模态） | 语音、视觉、桌面情景 → 结构化事实 → 提示词 | ✅ 已实现（立项时为全缺：全仓 `asr`/`whisper` 零命中） |
| **主动链路**（会自己开口） | 触发 → 节制 → 复用对话图 → 推送 | ✅ 已实现（立项时后端无推送通道，无法主动把消息送到界面） |

> **最容易被低估的一条**：主动沟通的**物理前提是服务端能推送**。
> 现状前端只有 `POST /chat` 请求-响应，后端没有任何通道能把一条消息送进界面。
> 不加推送通道，触发器写得再漂亮也送不出去。这是 P1 必须先做的原因（§5.1）。

### 0.1 三条「让开口有由头」的能力（§4.8 / §4.9）

P1–P4 做完之后，链路是通的，但**开口的由头很薄**：角色只知道「此刻在听什么歌」
「现在几点了（如果桌宠窗开着）」。它不知道今天星期几、不知道你已经在电脑前
坐了三小时、不知道你平时是什么节奏。于是主动开口容易退化成空泛问候。

补的是三样（**零新依赖、零模型成本**）：

| 能力 | 补什么 | 为什么原来没有 |
| --- | --- | --- |
| **时间感** | 日期 / 星期 / 时段，服务端权威 | 原先只在桌面情景上报里，Web 端永远没有、桌宠窗关着也没有 |
| **行踪** | 「几点到几点在用什么程序」，按段记录 | 快照 TTL 只有 120 秒，刻意不留历史 |
| **偏好画像** | 常用应用 / 活跃时段 / 深夜占比（**确定性计数**） | 完全没有；说出来的偏好由冷层记忆管，做出来的偏好没人管 |

这三样同时是**注入提示词的事实**与**主动触发器的判据**：
`back-from-away`（久离回来打个招呼）与 `activity-shift`（从工作切到娱乐 → 「忙完了？」）
都建在行踪之上（§5.2）。

## 3. 总体架构：三条链路

```
┌─────────────── 感知链路（输入多模态，新增） ───────────────┐
  ASR(语音)   视觉(图片/屏幕)   桌面情景(歌/窗口/时段/空闲)
      └────────────┬──────────────────┘
                   ▼
        PerceptionEvent（中性结构化事实，非提示词）
                   ▼
        LAYER_PERCEPTION → PromptManager（TTL + 预算上限）
                   │
                   ▼
        ┌──────── chat_graph（唯一生成通路）────────┐
        │  人设 + 世界书 + 记忆 + 感知 + 文风 → LLM  │
        │  情绪链路 → SSML/KA → 驱动时间轴          │
        └────────────────┬─────────────────────────┘
                         │ 用户主动输入
   ┌─────────────────────┴─────────────────────┐
   │                                           │
┌──▼──────────── 主动链路（新增）───────────┐   │
  Trigger（定时/间隔/事件/情景/记忆到期）
      ▼
  Gate 节制层（免打扰/冷却/配额/忙碌）──skip──▶ proactive_skipped
      ▼
  Intent（意图，不是文案）
      ▼
  合成内部消息 ──▶ 复用 chat_graph（proactive=true）
      ▼
  EventBus ──SSE──▶ 前端（数字人开口 + 气泡 + 通知）
```

**两条硬约定**（贯穿全文，写进代码前先看这两条）：

1. **感知源只产出中性事实，不产出提示词**——渲染由 `perception/context.py` 统一做。
   理由同 §9.4 的 `datasource` 分工：多源共享一套渲染，否则每个源各写一套中文句子，迟早漂移。
2. **主动消息必须走同一条 `chat_graph`，不另起炉灶**（§5.4）。
   理由：另写一套生成 = 人格漂移 + 两处维护。

## 4. 感知链路设计

### 4.1 接口与落位

新增 `backend/app/perception/`，**复用项目既有的扩展点范式**（§9.1 的
`base.py(ABC) + factory.py(按名创建) + config 字符串开关`），并按 §9.10 收编为
一个 `builtin` 插件 **`perception`**（能力族注册，不按实现名拆）：

```
backend/app/perception/
  base.py          # PerceptionSource 接口 + PerceptionEvent 模型
  factory.py       # 按名创建（config: PERCEPTION_SOURCES）
  context.py       # 感知事实 → 提示词片段（唯一渲染处）
  asr/             # 语音识别源
  vision/          # 视觉源
  desktop/         # 桌面情景源（接收 Electron 上报，不自己采集）
```

```python
class PerceptionEvent(BaseModel):
    source: str          # "asr" | "vision" | "desktop"
    kind: str            # "now_playing" | "user_speech" | "user_image" | ...
    payload: dict        # 中性字段，不含中文句子
    confidence: float
    observed_at: datetime
    ttl_seconds: int     # 过期即丢——感知是易失的，不该污染长期上下文
```

### 4.2 三类感知源

| 源 | 采集在哪 | 传什么 | Web 端 | 桌宠端 |
| --- | --- | --- | --- | --- |
| `asr` | 前端录音（MediaRecorder）→ 后端 | 音频 blob | ✅ | ✅ |
| `vision` | 前端选图 / 上传 → 后端 | 图片 | ✅（**仅用户主动**） | ✅（**仅用户主动**） |
| `desktop` | **Electron 主进程**采集 → IPC → 渲染层 → 后端 | 结构化字段 | ❌ 降级（无情景） | ✅ |

**`desktop` 的进程边界**（对齐 §4「主进程不接触任何模型 API Key，不代理业务请求」）：

```
Electron 主进程（只采集，不判断、不联网）
  SMTC 正在播放 / 前台窗口标题 / 空闲秒数 / 电量 / 时段
        │  IPC（新增通道，白名单校验，见 src/shared/ipc.ts）
        ▼
渲染层 → POST /perception/desktop
```

主进程**不直连后端**——业务请求一律由渲染层直连，这是既有约定（`desktop-pet.md` §4）。
采集结果只是一堆字段，**不含任何密钥**。

### 4.3 ASR：具体形态（✅ 已决策：**本地 faster-whisper**）

provider 化，走 §9.5 的**声明式配置**（`settings_schema` + `RUNTIME_OVERRIDABLE_FIELDS`）：

| provider | 依赖 | 状态 |
| --- | --- | --- |
| **`local`（faster-whisper）** | **新增依赖** | ✅ **本次采用**——离线、免费、语音数据不出本机 |
| `openai_compatible` | 零新依赖（复用现有 openai SDK） | ⏸️ 保留 provider 位，不做实现（将来换云端只加一个实现名） |
| `none` | — | 未配置/加载失败时的降级：界面上**不出现麦克风**，不是"点了没反应" |

#### 打包与模型体积（**必须按 §3.2 的原则处理**）

`faster-whisper` 不是「一个 pip 包装完就没事」——它拖三样东西进来：

| 引入项 | 影响 | 处理 |
| --- | --- | --- |
| `faster-whisper` + `ctranslate2` + `onnxruntime` + `av` | 安装包体积上涨，且都是**原生扩展** | ✅ **已实测可装**（见下） |
| Whisper 模型权重（`tiny`/`base`/`small`） | **绝不打进发布包**——与 §3.2「模型不入发布包」同一条原则 | 放 `%APPDATA%/HyPRA/models/whisper/`，由用户自备（已加进 `.gitignore`） |
| 许可证 | 按 §6 需进 `THIRD_PARTY_LICENSES/` 与依赖审计 | 逐项核对（均 MIT / Apache-2.0） |

**实测结论（2026-09，Windows + Python 3.13.7）**：

| 项 | 结果 |
| --- | --- |
| 依赖可装性 | ✅ `ctranslate2 4.8.2`（cp313 win_amd64）、`onnxruntime 1.30.0`（cp313）、`av 18.1.0` 都有 wheel，`faster-whisper 1.2.1` 装得上 |
| 下载体积 | 约 70 MB wheel |
| **清华镜像没有 `faster-whisper`** | ⚠️ 必须带官方源：`pip install -i https://pypi.tuna.tsinghua.edu.cn/simple --extra-index-url https://pypi.org/simple ".[asr]"` |
| **HuggingFace 直连被挡**（代理 502） | ⚠️ 拉模型要 `HF_ENDPOINT=https://hf-mirror.com` **且** `HF_HUB_DISABLE_XET=1`——新版 Xet 传输后端会绕过镜像直连 `cas-server.xethub.hf.co`，报 401 |
| 真实转写 | ✅ `tiny` 1.5s 音频 0.35s 出结果；`small` 亦可 |
| **PyInstaller 冻结形态** | ✅ **已实测可用**（见下） |

> 这两条网络坑正是「**不静默下载**」这条设计决策的现实依据：
> 模型缺失时报一句「请放到 `<数据目录>/models/whisper/<规格>/`」，
> 比让 faster-whisper 自己去拉、然后抛一段 HuggingFace 的连接栈有用得多。

#### 打包实测：两处必须显式声明，否则冻结形态直接不可用

`pyinstaller backend.spec` 已实测通过（构建约 84s，产物 `dist/backend/`）。
**PyInstaller 的静态分析收不全这套依赖**，spec 里加了两处显式收集
（两处都只在装了 `[asr]` 时才生效，用 `try/except ImportError` 包住——
**不装 ASR 也必须能构建成功**，那是一种受支持的形态）：

| 漏掉什么 | 后果 | 处理 |
| --- | --- | --- |
| `faster_whisper/assets/silero_vad_v6.onnx`（1.2MB） | 包内**按相对路径**加载，冻结后找不到 → `vad_filter=True` 直接 `FileNotFoundError`，**语音输入整个不可用** | `collect_data_files("faster_whisper")` |
| `ctranslate2/ctranslate2.dll`（**57MB**） | 它是包目录下的**普通 DLL**，不是扩展模块——PyInstaller 只自动收 `.pyd` 与 Python 包，普通 DLL 要显式收集。缺了它 `import ctranslate2` 直接失败 | `collect_dynamic_libs("ctranslate2")` |

`onnxruntime` 与 `av` 不用管：`pyinstaller-hooks-contrib` 已有它们的 hook
（`hook-onnxruntime.py` / `hook-av.py`）。`tokenizers.pyd` 是扩展模块，自动收。

**体积代价**（实测）：

| 形态 | 产物大小 |
| --- | --- |
| 含 ASR（装了 `[asr]`） | **317 MB** |
| 不含 ASR（未装 `[asr]`） | 约 140 MB |

ASR 一项占约 **176 MB**（`ctranslate2` 60M + `av.libs` 63M + `onnxruntime` 36M
+ `hf_xet` 9.1M + `tokenizers` 7.5M）。这个数字**支持把它留在可选依赖里**：
语音输入是增强，让不想用它的人少背 176MB 是合理的。

**冻结形态验证结果**（`dist/backend/backend.exe`，`ASR_MODEL=tiny`）：

```
GET  /health             → status ok；proactive running；六个触发器齐全
GET  /perception/status  → asr_available: true
POST /perception/asr     → "这句话又来对比不同情绪下的声音"（0.57s，与原文一致）
POST /perception/desktop → 此刻: - 现在是 02:14 / - 用户正在听《起风了》
GET  /events (SSE)       → perception_hint(ready) → proactive_message
POST /proactive/run      → daily-greeting 命中，生成角色化回复并推送
```

即：**感知 → 注入 → 主动开口 → 推送**这条链在冻结形态下与开发形态行为一致。

> ⚠️ 一个只在冻结形态才暴露的坑：**SSE 的作用域必须与主动链路解析出的角色一致**。
> 用 `persona_id=A` 订阅、而偏好指向 B 时，`run_once` 会认为「没人监听」而跳过
> ——响应里 `fired:false` 且 `skipped_reason` 为空，看起来像「没有意图」，
> 实际是作用域不匹配。排查时先对一下两边的人设 id。

#### 「幻听」：为什么 VAD 不是调优而是正确性

实测发现：**Whisper 在没有人声的音频上不会返回空串，而是吐出训练集里的水印文本**。
`small` 模型 + 一段 440Hz 纯音 → 识别结果是 **「字幕by索兰娅」**。

这在语音输入场景里是真问题：麦克风拾到环境噪音 / 键盘声 / 纯音乐时，
这句水印会被当成用户说的话**填进输入框**——用户会以为「它自己乱打字」。

两道防线（都已实现）：

| 防线 | 作用 |
| --- | --- |
| `ASR_VAD_FILTER=true`（Silero VAD 预切非语音段） | 从源头让模型「听不到」没人声的部分 |
| provider 里的文本过滤 | 兜住 VAD 漏掉的（有声音但非人声：音乐、键盘声） |

过滤**只认锚定在开头的固定套路**（`^字幕` / `^请订阅` / `^thanks for watching` …）
并加了 50 字上限。刻意不用「包含关键词」判据——那会误杀
「我订阅了那个频道」这种正常发言，而**误杀用户的话比漏掉一句水印严重得多**。

两条实现约束（都有前例可循）：

1. **模型要预加载**：首次调用才加载模型会让第一次说话等十几秒。
   参照现有 `main.py` 的 `tts_warmup_task`，lifespan 里加了 `asr_warmup_task`——
   但**只在用户已启用 ASR 时才预热**，否则白白占内存。
2. **`local` 的 provider 名与配置解耦**：模型规格（`tiny`/`base`/`small`）、
   设备（`cpu`/`cuda`）、VAD 开关都是 `settings_schema` 里的独立键，
   换规格不必改 provider 名——否则「换模型」会变成「换 provider」，
   与 §9.10「按能力族注册、不按实现名拆」的粒度约定冲突。

**端到端形态（重要：默认不自动发送）**：

```
按住说话 / VAD 自动断句 → 上传 → 转写 → 填入输入框 → 用户确认后发送
```

理由：ASR 有误识别，自动发送会让「识别错一个字」直接变成「对话跑偏」。
**填入输入框让用户看一眼**，是零成本的保险。桌宠端气泡同理。

### 4.4 视觉感知（✅ 已决策：**Qwen2.5-VL，只做用户主动分享**）

| 路径 | 触发方式 | 风险 | 决策 |
| --- | --- | --- | --- |
| **用户主动分享**（选图 / 上传） | 用户点一下 | 低 | ✅ **已实现**（Qwen2.5-VL） |
| 摄像头 | 定时抓帧 | **高** | ❌ **不做**（已决策） |
| **连续屏幕感知**（定期截图） | 定时器 | **高**（隐私 + token 成本） | ❌ **不做**（已决策） |

**模型选型：Qwen2.5-VL，走 OpenAI 兼容端点**（`app/perception/vision/`）。

选它的关键理由是**零新依赖**：阿里百炼与硅基流动都提供 OpenAI 兼容的多模态端点，
而 `openai` SDK 已经在本项目里（`app/llm/openai_compatible.py`）。
按 `AGENTS.md §5`「新增第三方依赖前先列出方案」的口径，这条路不用新增任何依赖。

**这个决策的连带好处**（不只是"少做点东西"）：

- 采集链路里**没有定时器**，感知层就只剩「用户动作触发」一种形态——
  §4.6 的隐私红线大半自动成立（没有后台采集，就没有"关掉开关还在偷偷采"的风险）；
- 演示与截图**天然合规**：画面里出现的永远是用户自己主动放进来的内容，
  不需要为"演示素材不得含真实桌面情景"单独做约束（§8.6 的红线少一条要守）；
- token 成本**可预测**：每次视觉理解都由用户点击触发，不存在"挂机一晚烧掉多少"的问题。

**模型侧的影响（已处理）**：现有 `app/llm/profiles.yaml` 是**纯文本假设**，
因此 `VISION_MODEL` 是**独立配置项**，与 `LLM_MODEL` 解耦。

设计原则：**视觉理解的结果只作为感知事实注入，不改变对话链路**。
即「模型看图」和「模型对话」是两次调用、两个模型，互不干扰——
这样视觉模型缺失时，整个对话链路照常工作（降级友好）。

**两条实现纪律**（`app/perception/vision/openai_compatible.py`）：

1. **图片以 data URL 内联，不落盘**。「用户分享的图会不会被存下来」这个问题，
   最好的答案是没有那个文件。
2. **提示词要求「只描述看得见的」**。视觉模型天然爱做推断（「他看起来很疲惫」），
   而推断属于人设的职责——感知层只提供素材，把解读权留给模型。

**交互口径**：理解结果**只回填输入框的一句提示语**（「给你看一张图」），
描述本身由 `LAYER_PERCEPTION` 注入——写进用户消息等于说两遍，
而且会变成「用户转述了自己发的图」这种奇怪的角色。

### 4.5 感知 → 提示词注入

`PromptManager` 新增一层 `LAYER_PERCEPTION`，插入位置与三条约束：

```
世界书触发 > 【感知·此刻】 > 个人记忆 > 情景记忆 > 语义事实 > 滚动窗口
```

| 约束 | 理由 |
| --- | --- |
| **带 TTL** | 感知是易失的：5 分钟前听过的歌不该继续出现在上下文里 |
| **有独立预算上限** | 感知可能很长（屏幕 OCR），不能挤掉记忆层 |
| **渲染成第二人称事实，不是机器口吻** | 见下 |

渲染格式（`perception/context.py`，唯一渲染处）：

```
【此刻】
- 用户正在听《XXX》—— 林俊杰
- 现在是 02:14
```

**不给任何行动建议**——怎么用这些事实由人设决定。
写成「你应该关心用户熬夜」就等于把人设写死在了感知层。

### 4.6 隐私与合规（红线，与 §6 同级）

| 红线 | 落地 |
| --- | --- |
| 感知**默认全关**，逐项显式开启 | 与插件「默认启用」不同——感知是敏感的 |
| **不做任何后台采集** | 采集全部由用户动作触发（点麦克风 / 点上传）——见 §4.4 决策 |
| 原图**不落盘** | 视觉理解完成后即丢，只留结构化描述 |
| 感知数据**不进记忆库** | 除非用户明确确认——避免「我记得你上周三凌晨在听什么歌」这种越界 |
| 行踪**只记程序名**，且保留期有限、可一键清空 | §4.9；窗口标题是内容，程序名才是类别 |
| 免打扰可感知 | 检测到会议 / 全屏游戏 / 演示模式 → 不主动 |
| 演示素材 | **不得**用真实桌面情景截图（对齐 §8.6 勘察数据红线） |
| 关闭即停 | 关掉开关后采集链路**立即停止**，不是「采集了不用」；行踪还要连带清掉已有文件 |

### 4.7 入口可见性：能力有了，用户得知道

**问题**：语音与发图都是「**入口可见、能力不可见**」的功能——按钮摆在那里，
但用户不知道「点了会怎样」，尤其不知道「识别结果不会自动发送」，
于是不敢点。实测反馈就是一句「对话界面没有发送图片和语音的提示」。

**三条措施**（都不改能力本身，只改可见性）：

| 措施 | 落点 | 说明 |
| --- | --- | --- |
| **一次性上手提示** | `components/chat/CapabilityHint.tsx` | 输入区上方一条可关掉的提示，**文案里写明「不会自动发送」**（那正是用户不敢点的原因）；关掉后记在 localStorage，不再出现 |
| **按钮文案与 tooltip** | `MicButton` / `ImageButton` | 按钮本身带「语音」「图片」字样，tooltip 补充「识别结果会填进输入框，不会自动发送」与当前快捷键 |
| **空状态提示**（桌宠窗） | `pet/ChatBubble.tsx` | 桌宠面板只有 190px 宽，塞不下独立引导条，改由本来就要占位的空状态那句话承担 |

**只在确实有可用能力时才提示**：没有能力却提示「你可以发图」，
用户点不到按钮，只会更困惑。

---

#### 「能力」与「入口」是两个开关

三个新配置（都在插件设置里，`能力中心 → 语音识别 / 图片理解`）：

| 键 | 默认 | 作用 |
| --- | --- | --- |
| `ASR_UI_ENABLED` | `true` | 是否渲染语音按钮 |
| `VISION_UI_ENABLED` | `true` | 是否渲染「图片」按钮 |
| `ASR_SHORTCUT` | `""`（不启用） | 语音快捷键，形如 `Ctrl+Shift+M` |

**为什么分开**：关掉按钮 ≠ 关掉能力。接口照常可用，
快捷键也照常工作——这样「用快捷键说话、不想看见按钮」这种用法才成立。

两条实现细节：

1. **录音 / 转写中即使按钮被关掉也要显示**。快捷键不依赖按钮也能开录音，
   那时用户需要一个「正在录」的指示与停止入口——否则麦克风开着
   却没有任何可见的关闭方式。
2. **快捷键只在窗口获得焦点时生效**，不注册系统级全局热键。
   全局热键需要主进程介入，且会与用户的其它软件抢键——
   一个「陪伴」应用抢全局热键是很不礼貌的。

**快捷键的防误触**（`frontend/lib/chat/shortcut.ts`，纯函数、已单测）：

- 不带 `Ctrl`/`Alt`/`Meta` 的快捷键（如 `M`）**在输入框里让路**——
  否则用户打字打到 M 就开始录音。`Shift+M` 仍算「裸键」：那是在打大写字母。
- **修饰键精确匹配**：配了 `Ctrl+M` 时按 `Ctrl+Shift+M` 不触发，
  否则用户设的快捷键会与别人的互相串台。
- `event.repeat` 忽略：长按会连发 keydown，不拦会「开了又关」。

### 4.8 时间感：让角色知道「现在是什么时候」

**问题**：原先「现在是几点」只存在于 `DesktopContext.local_time` 里，
而那是桌宠端**上报**来的。于是它同时依赖「桌宠窗开着」与「上报没过期（120s）」
两个条件——**Web 端永远没有时间**，桌宠端在窗口关掉或用户进全屏应用
（上报被跳过）时也会丢。而且它只有 `HH:MM`：没有日期、没有星期、没有时段。

这不是人设的问题，是它真的不知道。模型不知道时间，就会在凌晨两点说
「今天过得怎么样呀」。

### 两条来源，一个格式

| 情形 | 用谁的时间 |
| --- | --- |
| 客户端上报了 `local_time`（桌宠端在线） | **客户端的**——那才是用户墙上的钟 |
| 没有客户端上报（Web 端 / 桌宠窗关着） | **服务端的本地时间** |

为什么保留客户端这条：docker compose 部署时后端可能在 UTC，而用户在 UTC+8。
为什么必须有服务端这条：Web 端拿不到桌面情景，**没有兜底就等于没有时间**。

两条来源归一成同一组中性字段（`date` / `hour` / `minute` / `weekday` / `origin`），
中文由 `perception/context.py` 唯一渲染——所以「桌宠端看到的」与
「Web 端看到的」**逐字一致**，不会出现两套措辞。

### 渲染形态

```
- 现在是 9 月 29 日 星期二 22:13，深夜
```

日期、星期、时段三样都给：模型据此才能分清「周末早上」与「工作日深夜」，
而这两个场景下该说的话完全不同。**年份刻意不给**——陪伴场景里它几乎无用，
而每轮多几个 token 是实打实的成本。

时段划分（`_PERIOD_RANGES`）：清晨 5–7 / 上午 8–11 / 中午 12–13 / 下午 14–17 /
傍晚 18–19 / 晚上 20–22 / 其余为深夜。

### 一个被替换掉的旧行为

`DesktopContext.local_time` **不再单独渲染**。同一个事实有两个来源就会有两套措辞，
而「时间」是全对话最基础的一条上下文——它只该有一个出处。
`local_time` / `local_date` 字段本身保留：`clock.time_fact` 仍然要用它
取「用户墙上的钟」（见上表），`LateNightTrigger` 也仍用它写触发原因。

配置：`perception_include_time`（**默认开**）。

### 4.9 行踪与偏好画像：让角色知道「你最近在忙什么」

**问题**：快照回答的是「**现在**在用哪个窗口」，TTL 只有 120 秒——它刻意不留历史。
于是角色只知道「此刻你在 VS Code」，不知道「你已经连着写了三个小时代码」
「刚刚从游戏里退出来」。

而后者才是能拿来**聊天**的东西：「忙完了？」「回来啦」——
一句有由头的话，前提是它知道刚才发生了什么。

### 为什么按「段」记，不按「次」记

上报每 30 秒一次。逐次落盘一天就是 2880 条「用户在用 Code.exe」，
既看不出结构，聚合时还要先去重。改成**段**（同一进程连续使用算一段）之后：

- 行踪天然是「09:10–11:40 在用 Code.exe」这种可读的形态；
- 数据量降到每天几十条；
- 「最近在忙什么」直接取最后几段就行，不需要额外推导。

### 存储形态

```
data/perception/
  activity-2026-09-29.jsonl   # 每天一个文件，一行一段（**只放已结束的段**）
  activity-current.json       # 当前正在进行的那一段（原子覆盖）
```

为什么当前段要**单独落一个小文件**而不是只等闭段：用户在 VS Code 里连着写三小时，
那三小时里一条记录都没有——画像与「最近在忙什么」会同时读到空。
每 30 秒原子覆盖一个几十字节的文件，代价可以忽略；顺带进程重启也不丢这一段。

### 空闲必须闭段

上报里的 `idle_seconds` 是「无键鼠输入的秒数」。人离开电脑时前台窗口
**仍然是那个窗口**——不处理的话会记出「用户连续 8 小时在用 VS Code」，
而那正是行踪最不能出的错（它把「不在」读成了「在」）。

所以空闲超过 `perception_activity_idle_gap_seconds`（默认 300s）时：闭段，
且段的结束时刻取 `now - idle_seconds`（**真正的最后一次操作**），
而不是「发现他离开的那一刻」。

### 偏好画像：确定性聚合，不调模型

最直觉的做法是把七天的行踪丢给模型写一段「他是个夜猫子，喜欢写代码」。
**刻意不这么做**：

| 理由 | 说明 |
| --- | --- |
| **可解释** | 「他最常用 Code.exe（12 小时）」能追到每一段行踪。模型写出来的「他热爱编程」追不到任何东西，错了也查不出来 |
| **零成本** | 画像每轮对话都要注入。走模型等于每轮多一次调用，而它只是几十条秒数的加法 |
| **不越界** | 模型爱做价值判断（「他工作压力很大」）。行踪只支持「他在用 XX」，不支持「他是个 XX 的人」——后者是人设该说的话 |

产出的是**计数与排序**：常用应用 TOP N、活跃时段、峰值三小时窗口、深夜占比。
措辞交给 `context.py`，解读交给 persona。

> **「偏好」有两半，这里只做行为的那一半**：说出来的偏好（「我喜欢下雨天」）
> 已经由冷层语义记忆（`FactType.PREFERENCE`）负责且常驻注入；
> 做出来的偏好（每天在用什么）此前完全没有。两半不重叠、不互相替代。

两条实现细节：

1. **样本不足就不出画像**（`perception_profile_min_minutes`，默认 30 分钟）。
   用两分钟的行踪说「他最常用 Code.exe」是不诚实的——那只是「他刚打开了 Code」。
2. **跨零点的段按小时摊分**。「夜猫子」这个判据全靠它：一段 22:50→00:20
   必须同时记进 22 点、23 点、0 点。峰值窗口也允许跨零点
   （22:00–01:00 才是夜猫子的峰值，写成 22:00–22:00 就没了意义）。

**画像依赖行踪**：`perception_activity_enabled` 关掉时，
`perception_profile_enabled` 也自动失效。这不是「多一道保险」，
而是语义上的依赖——画像**没有别的数据来源**。
两个开关分开，是为了让用户能「记行踪，但不要它总结」，
而不是「关了行踪还能总结」（那等于开关是假的）。

### 进程 → 类别：复用 `busy.py` 的表

行踪给每个进程打一个类别（`dev` / `office` / `design` / `browser` / `chat` /
`media` / `game` / `meeting` / `tool` / `other`），用于「从工作切到娱乐」这类判断。

会议 / 游戏 / 视频三类**直接复用 `busy.py` 的进程表**，不另抄一份——
那三张表已经为「忙碌判定」维护过一轮，抄一遍迟早两边不一致
（会出现「忙碌判定说在开会、行踪说在聊天」这种自相矛盾）。

### 注入形态

```
- 现在是 9 月 29 日 星期二 22:13，深夜
- 用户正在听《起风了》—— 买辣椒也用券
- 最近 3 小时，他用得最多的是 Code.exe（约 1 小时 20 分钟），也用过 chrome.exe
- 最近 7 天，他最常用 Code.exe（约 12 小时），其次是 chrome.exe（约 3 小时）
- 他通常在 20:00–23:00 这段时间用电脑
```

顺序是**从最当下到最长期**：时钟 → 快照事实 → 行踪 → 画像。
注入位置越靠前对生成的锚定越强，而「此刻」这一层里最该被锚定的是时间。

两条刻意的裁剪：

| 裁剪 | 理由 |
| --- | --- |
| 行踪**只报用得最多的那一个**（+ 最多两个超过 5 分钟的） | 逐段罗列会变成流水账，既占预算又不会让回答更贴切 |
| 不足一分钟**不报时长** | 段刚开出来时它是「0 秒」，写进提示词只会让模型盯着那个数字看 |
| 画像**最多三行**，第二名占比不足 15% 不列 | 否则会写出「他最常用 Code.exe，其次是计算器」这种把噪音当偏好的句子 |

### 汇集层：四个来源，一个入口

感知事实现在有四个来源（快照 / 时钟 / 行踪 / 画像），
但消费方（对话路由 / 状态接口 / 主动链路）只该看到一个入口——
`perception/gather.py: current_events()`，渲染入口是
`perception/context.py: render_current()`。

不让三处调用点各自去拼的理由很实在：那样会出现「对话里有时钟、状态接口里没有」
「主动开口看不到行踪」这类不一致，而且**加一个来源要改三处**。
「汇集」与「渲染」也刻意绑在一个入口里——拆开调用时极易漏掉「先汇集」，
而漏掉的表现是静默地什么都不注入（`render_perception([])` 是合法的空串）。

### 隐私红线（与 §4.6 同级，逐条落地）

| 红线 | 落地 |
| --- | --- |
| 行踪**默认只记程序名** | 窗口标题需要显式开 `perception_activity_include_title`。程序名是**类别**（`Code.exe`），标题是**内容**（可能是一份体检报告）——同 `busy.py` 的判据取舍 |
| **不记内容** | 没有按键、没有剪贴板、没有 URL、没有文件路径 |
| **不进记忆库** | 行踪只服务「此刻」的注入与触发判断；不写进温层/冷层，因此不会出现「我记得你上周三凌晨在听什么歌」 |
| **保留期刻意短** | 默认 7 天。行踪是敏感数据，够用就好——留得越久越像在攒档案 |
| **可一键清空** | `POST /perception/activity/clear`，一次清干净（只清一半反而让人怀疑「到底删了没」）；清空同时作废画像缓存 |
| **关掉即停止** | 关掉 `perception_activity_enabled` 后：不再记录，**且清掉已有文件**；关掉 `perception_desktop_enabled` 同理（行踪的唯一数据源就是它） |
| **可见** | 桌宠设置面板里逐段列出「它到底记了什么」，并说明记了什么、没记什么 |

> 最后一条容易被当成「锦上添花」，其实是前提：用户只能靠它说的话去猜自己被记了什么，
> 而**猜出来的结论一定比实际更糟**。



## 5. 主动沟通设计

### 5.1 物理前提：服务端推送通道（P1 先决条件）

现状前端只有 `POST /chat` 请求-响应，后端**无法**主动把消息送到界面。补一条：

```
GET /events?scope=companion:{id}     # SSE
```

**选 SSE 而不是 WebSocket**：

| 理由 | 说明 |
| --- | --- |
| 主动消息本就是**单向**（服务端 → 客户端） | 不需要双向 |
| 走 HTTP，**零新依赖** | FastAPI 原生 `StreamingResponse` 即可 |
| 浏览器**自动重连** | 省掉一套重连逻辑 |
| 反代 / 防火墙友好 | 与现有部署方式（docker compose）无冲突 |

事件类型（前端按 `type` 分派）：

| type | 用途 |
| --- | --- |
| `proactive_message` | 主动开口：`{reply, emotion, speak}`——**结构与 `/chat` 响应一致**，前端复用同一套渲染 |
| `perception_hint` | 感知状态提示（如「正在听歌」徽标） |
| `proactive_skipped` | 被节制层拦下：`{trigger, reason}`——**可观测性**，调参靠它 |

> ⚠️ **单进程假设**：后端开发/打包形态都是单进程 uvicorn，因此事件总线用
> **进程内 pub/sub** 即可，不做多 worker 广播。这一点必须写进代码注释，
> 否则将来上多 worker 会出现「消息随机丢失」且极难定位。

### 5.2 触发源（Trigger）

```python
class ProactiveTrigger(ABC):
    id: str
    def evaluate(self, ctx: ProactiveContext) -> ProactiveIntent | None: ...
```

| 触发源 | 判据 | 举例 |
| --- | --- | --- |
| **定时** | 每日固定时刻 | 早上 8:00 打招呼 |
| **间隔** | 距上次互动 > N 小时 | 半天没聊，问一句 |
| **事件** | 订阅事件总线 | 用户上线 / 会话结束 |
| **情景** | 感知事实匹配 | 凌晨 2 点还在活动、听到某首歌 |
| **记忆到期** | 冷层事实的 follow-up 时间到了 | 「你上次说妈妈身体不好，检查结果出来了吗」 |
| **行踪**（§4.9） | 段的变化 | 离开两小时后回来（`back-from-away`）、从写代码切到打游戏（`activity-shift`） |
| **空闲维护** | 系统空闲（借 Araya 思想） | 整理记忆 / 生成日记——**静默，不打扰用户** |

**关键**：触发器只产出**意图（intent）**，**不产出文案**。文案一律由对话链路生成。

#### 两个行踪驱动的触发器

| 触发器 | 判据 | 为什么值得单独存在 |
| --- | --- | --- |
| `back-from-away` | 离开超过 N 分钟（默认 30）后刚回到电脑前 | 这是**唯一**一种「用户什么都没做、但状态变了」的时刻。别的触发器要么是「时间到了」要么是「有事发生」，只有它是「他回来了」——而那句「回来啦」是陪伴感最直接的形态 |

**判据来自行踪，不是 `idle_seconds`**：空闲秒数在用户回来之后**立刻归零**，
拿它判「他刚才离开了多久」在结构上就做不到。行踪里
「上一段结束」与「这一段开始」之间的空隙才是离开时长（`ActivitySummary.away_seconds`）。

| 触发器 | 判据 | 为什么值得单独存在 |
| --- | --- | --- |
| `activity-shift` | 从写代码 / 文档 / 设计切到游戏 / 看片，且新段已持续 ≥ N 分钟（默认 20） | 「忙完了？」是最自然的搭话时机 |

**只做一个方向**（做事 → 放松）：反方向正是用户要进入状态的时候，开口就是打断。
这个不对称是有意的——陪伴要出现在「可以被打断」的时刻，而不是「不该被打断」的时刻。

两个触发器的**去重键都用当前段的开始时刻**：每次回来 / 每次切换都是一个新时刻，
因此都能说一句；真正的频率控制交给闸门③（冷却 30 分钟）与闸门④（每日配额）——
这正是 §5.3 说的「真正防轰炸的是冷却与对话中不插话，不是去重」。

#### 「有由头才开口」的落地

`daily-greeting` 与 `idle-checkin` 这两个**本来没由头**的触发器，
会把行踪与画像拼进 `reason` 与 `facts`：

```
reason: 到了每天 09:00 这个时刻，可以自然地打个招呼。你注意到：最近 3 小时，
        他用得最多的是 Code.exe（约 2 小时）。
facts:  ["最近 3 小时，他用得最多的是 Code.exe（约 2 小时）",
         "最近 7 天，他最常用 Code.exe（约 12 小时）"]
```

理由见 §5.4：主动开口必须**有由头**，否则就是一句空泛的问候。
「你最近一直在写代码，今天也顺利吗」与「早上好」是完全不同的两句话。
`reason` 同时是记忆召回的 query，带上具体信息也能召回到更相关的记忆。

裁剪是有意的：画像**只取第一行**（最常用的那个应用）——画像整体已经由
感知层 `[此刻]` 注入了，`facts` 里再全量重复一遍只是白占预算。

```python
class ProactiveIntent(BaseModel):
    trigger_id: str
    reason: str        # 给模型看的触发原因（内部，非用户可见）
    urgency: float     # 0-1，影响闸门与文案长度
```

### 5.3 节制层（Gate）—— 主动沟通能不能用，全看这一层

**串行闸门，任一不过就 skip**（并广播 `proactive_skipped` 记下原因）：

| # | 闸门 | 默认值 |
| --- | --- | --- |
| 1 | 总开关 | ✅ **默认开**（已决策）；关则全停 |
| 2 | 免打扰时段 | 23:00–08:00（**关怀型触发 + 感知到用户清醒**可豁免） |
| 3 | 冷却：距上一条主动消息 | ≥ **30 分钟** |
| 4 | 每日配额 | ≤ **12 条** |
| 5 | 用户正在对话中（距上次输入 < 2 分钟） | skip——此时该**回应**，不该另起话头 |
| 6 | 感知到忙碌（会议 / 游戏 / 全屏视频进程） | skip |
| 7 | 同一触发器当日重复 | skip |

> **默认开 = 上面 2–7 条必须同时默认生效**。这是这次决策的完整含义：
> 不是因为"演示好看"就放开，而是「**开着的默认值本身就是克制的**」——
> 免打扰、冷却、每日配额、对话中不插话，这几条默认就在管着。
> 用户不需要先做配置才不会被骚扰；他什么都不设，体验也已经是收敛的。
>
> 反向也要成立：**关总开关必须是一键、且立即生效**，不留"这轮已经排好了"的尾巴。

#### 频率默认值上调过一轮（闸门③④与间隔触发器）

| 参数 | 初版 | 现值 | 为什么改 |
| --- | --- | --- | --- |
| 冷却（闸门③） | 90 分钟 | **30** | 仍能保证「不会连着两句」 |
| 每日配额（闸门④） | 6 条 | **12** | 6 条 ≈ 每条间隔 1.5 小时，陪伴感偏弱 |
| 静默阈值（间隔触发器） | 6 小时 | **3** | 半天不说话才被问一句，太晚了 |
| 免打扰（闸门②） | 23:00–08:00 | **不变** | 它是「不烦人」的底线，不是频率旋钮 |
| 对话中不插话（闸门⑤） | 2 分钟 | **不变** | 同上 |

**改的只是默认值，闸门机制一字未动。** 这条值得单独记下来，因为它是一次
「产品判断覆盖工程直觉」的调整：初版按「宁可少说」定档，工程上更安全，
但实测下来——一天 6 条、每条间隔一个半小时——用户要的是「它会主动找我」，
而不是「一天问候一次」。

真正防轰炸的是闸门③（不会连着说）与闸门⑤（你在说话时它不插嘴），
不是配额上限。**把配额当成主要防线，是初版定档时的思路错位。**
想要更安静的用户把这三个数改回去即可（`.env` 或能力中心）。

> **这一层必须是纯函数 + 可单测**，对齐项目里 `petGeometry.ts` /
> `avatar-source.ts` 的「纯函数 + 单测钉住」风格。
> 主动沟通的体验成败**九成在节制**：漏一次是打扰，漏十次是骚扰。

### 5.4 意图 → 文案：复用对话图，不另起炉灶

**硬约定**：主动消息必须走**同一条 `chat_graph`**。做法是合成一条内部消息：

```
[系统提示·非用户输入] 触发原因：用户凌晨 2 点还在活动。
请以你的身份，自然地开口说一句。
```

带 `proactive=true` 标记，各层的处理：

| 层 | 处理 | 理由 |
| --- | --- | --- |
| 提示词 | 追加「主动开口」约束片段（更短、更像搭话、**不追问**、给用户不回应的空间） | 主动开口 ≠ 回复 |
| 记忆 | **照常写入**情景记忆 | 它是真实发生过的对话 |
| 情绪 | **照常**走 function calling | 主动开口也有情绪，表情该跟着变 |
| 输出 | **照常** SSML → 前端 `speak()` | 复用既有链路，零新代码 |
| 记忆召回 | 以 `intent.reason` 为 query 做一次召回 | 主动开口必须「有由头」，否则就是空泛的问候 |

**并且允许模型拒绝**：`ProactiveIntent` 的生成端允许返回 `decline`（此刻不说话）。
这比硬生成一句更有人格——对齐「输出格式约束层」的思路：先给模型「可以不开口」的自由度。

### 5.5 触达通道

| 通道 | Web 端 | 桌宠端 | 说明 |
| --- | --- | --- | --- |
| 数字人开口 | ✅ | ✅ | 复用 `speak()` 链路 |
| 气泡 / 字幕 | ✅ | ✅ | 复用现有组件 |
| 系统通知 | ❌ | ✅（Electron `Notification`） | 桌宠被遮挡时 |
| 未读标记 | ✅ | ✅ | 用户没看到时的兜底 |

### 5.6 伦理边界（写进文档 **且** 写进提示词）

| 边界 | 落地 |
| --- | --- |
| **不制造依赖** | 禁止「你都不理我了」这类情感勒索话术——进人设预设的 `<boundary>` 段 |
| **不假装真人** | 对齐 `jailbreak-layer.md` 的 boundary 约定 |
| **危机信号优先** | 感知到危机信号 → 走危机响应，**不走**主动闲聊 |
| **全权可关** | 用户能关总开关，也能逐触发器关 |

| 赛题自由度 | 本期补的是什么 | 对应评分点 |
| --- | --- | --- |

> 而是**知道此刻发生了什么、并据此开口**的存在。
> 这条也直接强化 `why-embodied-avatar.md` 的主张 2（时间的连续性）——
> 「它记得我，而且**会主动找我**」比「我问它才答」是量级差异的关系体验。

## 8. 决策记录

### 8.1 已定（✅）

| # | 决策 | 结论 | 落到哪 |
| --- | --- | --- | --- |
| 1 | **ASR 选型** | **本地 `faster-whisper`** | §4.3（含打包与模型的处理） |
| 2 | **摄像头 / 连续屏幕感知** | **不做**；视觉只走「用户主动分享」 | §4.4、§4.6 |
| 3 | **主动消息默认开关** | **默认开**，且 §5.3 的 2–7 条节制**同时默认生效** | §5.3 |
| 4 | **视觉模型** | **引入 Qwen2.5-VL**，走 OpenAI 兼容端点（**零新依赖**） | §4.4 |

**这四条之间是有内在一致性的**，不是四个独立选择：

> 全部采集都由**用户动作触发**（无后台定时器） + 主动消息**默认开但默认克制** =
> 这个系统不会在用户不知情的时候做任何事。
> 「默认开」之所以敢开，正是因为**采集端没有后台行为、发送端有七道闸门**。

视觉选 Qwen2.5-VL 还带来一条降级性质：**它与对话模型是两次调用、两个模型**，
因此没配 VL 模型时，整个对话链路照常工作——把两者绑在一起的话，
没配视觉就会连聊天都用不了。

#### P5 的三条（§4.8 / §4.9）

| # | 决策 | 结论 | 落到哪 |
| --- | --- | --- | --- |
| 5 | **时间来源** | **客户端优先、服务端兜底**；两条来源归一成同一组中性字段 | §4.8 |
| 6 | **偏好画像的产出方式** | **确定性计数，不调模型** | §4.9 |
| 7 | **行踪的默认粒度** | **只记程序名**，保留 7 天，可一键清空 | §4.9 |

三条同样有内在一致性：

> **能不用模型就不用模型**（画像是加法）、**能少记就少记**（只记类别不记内容）、
> **能看见就能清掉**（逐段可见 + 一键清空）——
> 这三条合起来是「行踪这种敏感能力可以被接受」的前提。

第 5 条的理由单独说一句：为什么不做成「只用服务端时间」？
因为 docker compose 部署时后端在容器里（可能是 UTC），
而免打扰时段、深夜关怀这些判断依据的必须是**用户墙上的钟**。
反过来，为什么不做成「只用客户端时间」？因为 Web 端拿不到桌面情景——
那等于 Web 端永远没有时间。**两条都要，且必须归一成同一个格式。**

#### 实机冒烟发现的问题（都已修）

前三条来自 P1–P4 的实机冒烟，第 4–6 条来自 P5（行踪）的实现与冒烟。

| # | 现象 | 根因 | 处理 |
| --- | --- | --- | --- |
| 1 | 纯音被转成「字幕by索兰娅」 | Whisper 在无人声音频上吐训练集水印 | `ASR_VAD_FILTER` + 文本过滤（见 §4.3） |
| 2 | 注入 provider 的替身不生效 | `set_asr_provider` 把配置签名置空，下一次 `get` 认为「配置变了」而重建 | 注入时把签名**对齐当前配置** |
| 3 | 主动链路每轮撞一次 404 | 偏好里的角色已被用户在创作工坊里删除（删除写用户侧隐藏清单） | `_resolve_persona` 校验角色仍在，不在就静默跳过 |
| 4 | 行踪段「刷新一次就不算进行中了」 | `ActivitySegment.ongoing` 原先是「起止时刻相等」，而段一旦被刷新 `ended_at` 就往后推了 | 改成显式布尔字段；约束：**日文件里恒为 False**，只有内存当前段与 `activity-current.json` 为 True |
| 5 | **在控制台关掉行踪后，文件仍留在盘上** | 清理只写在 `POST /perception/desktop` 里，而那条路要求桌宠端在跑——用户完全可能「先关开关，再关掉桌宠窗」 | 抽出幂等的 `sync_activity_switch()`，挂到**配置变更钩子**（`api/plugins.py`）与每次上报两处 |
| 6 | 清除接口把不存在的文件也算进删除数 | `unlink(missing_ok=True)` 对不存在的路径也成功；`activity-*` 又已涵盖 `activity-current.json`，被数了两次 | 只 glob 一次 + 只数真正存在的文件 |

> 第 3 条尤其值得记：它只在「用户动过角色列表」之后才出现，
> 而表现是「调度日志一直报未知人设」——真正该做的只是跳过这一轮。

> 第 4 条值得记的是它的**发现方式**：单跑 `tests/test_proactive` 时是绿的，
> 全量跑才红——因为另一条用例先改动了时间轴。两个触发器（`back-from-away` /
> `activity-shift`）与画像的跨零点摊分**同时**依赖 `ongoing`，所以那一个字段错了
> 会同时表现为「不再主动说话」与「夜猫子判据失效」，而两者看起来毫不相关。
> 教训：**用「两个字段相等」表达状态，等价于把不变量藏在数据里**。

> 第 5 条是**只有真跑起来才会暴露**的那一类：单元测试里「关掉开关」的用例
> 都是「关掉 → 再上报一次 → 断言清空」，而现实中用户恰恰会跳过中间那一步。
> 教训：**「关闭」的语义要在「配置变更的那一刻」兑现，不能搭在另一个动作的顺风车上。**
