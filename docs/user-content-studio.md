# 用户自定义角色、世界书与文风（创作工坊）

> 让用户自己创建对话角色（人设 + 背景故事）、世界设定（按条件触发的世界书条目）
> 与说话方式（文风预设）。
> 数据契约、接口与不变量的唯一权威说明；实现见 `backend/app/studio/` 与
> `backend/app/api/studio.py`，前端面板见 `frontend/components/studio/StudioPanel.tsx`。

## 1. 定位

内置人设（如 `therapist-elder-sister`）与世界书条目是**项目自带**的原创内容，包内文件不可直接修改。
创作工坊允许用户复制、停用或从当前工坊删除这些内置资源；删除只写用户侧隐藏清单，不改包内文件。
创作工坊让用户在自己的机器上扩展这三类内容：

| 用户能做的 | 对应概念 |
|---|---|
| 创建一个对话角色：角色名 / 一句话定位 / 简介 / 标签 / **人设正文** / **背景故事** | 角色卡（persona） |
| 写「背景故事」：这个角色的过往与世界观，每次对话都会带上 | 人设正文的补充块 |
| 写「世界书条目」：命中某个条件才注入的设定补充 | 世界书（World Info）条目 |
| 决定条目对谁生效：所有角色，或某个专属角色 | 条目归属 `scope` |
| 写完立刻试：给一句「用户可能会说的话」，看会不会触发 | 试触发 |
| 写「文风」：风格指令 / 避免表达 / 示例对话 / 建议采样参数 | 文风预设（style） |

概念边界（四层，各管一段，互不重叠）：

```
人设正文   →  「她是谁」——常驻，角色层的开头
背景故事   →  「她的过往与世界观」——常驻，角色层的末尾
世界书条目 →  「什么情况下补充什么设定」——按关键词 / 正则 / 语义触发
文风预设   →  「怎么说话」——追加在 system 末尾 + few-shot 示例，与角色**正交**
```

**为什么文风要独立成一层而不是塞进角色卡**：人设（是谁）/ 文风（怎么说话）/
模型适配（这个模型吃哪套）三者正交。同一个人设配「简短利落」和配「古典雅致」是
两种完全不同的陪伴体验，而用户往往想对同一个角色反复试。做成角色卡的一个字段，
就等于每换一次文风都得复制一份角色——而角色 id 是记忆隔离命名空间，
复制角色等于换一整套记忆。

## 2. 数据契约

### 2.1 目录

    backend/data/studio/                    # 用户本地数据（backend/data/ 已被 .gitignore 覆盖）
      personas/<id>.yaml                    # 我创建的角色卡（与内置角色**同构**）
      personas/deleted_builtin.json         # 从当前工坊隐藏的内置角色 id（内置文件一字未改）
      worldbook/<id>.yaml                   # 我创建的世界书条目（与内置条目**同构**）
      worldbook/disabled_builtin.json       # 我停用掉的内置条目 id（内置文件一字未改）
      worldbook/deleted_builtin.json        # 从当前工坊隐藏的内置条目 id（内置文件一字未改）
      styles/<id>.yaml                      # 我创建的文风预设（与内置文风**同构**）
      styles/deleted_builtin.json           # 从当前工坊隐藏的内置文风 id（内置文件一字未改）

目录由 `STUDIO_DIR` 配置（默认 `data/studio`，相对 `backend/` 运行目录）。

**同构**是这里最重要的设计：用户内容与内置资源共用同一套 pydantic 模型
（`PersonaPreset` / `WorldBookEntry` / `StylePreset`），因此自建角色在对话链路上与内置角色
**没有任何差异**——加载器只是多扫一个目录。这样「用户能做的」与「内置能做的」
不会分叉成两套逻辑。

### 2.2 角色卡 YAML

```yaml
id: user-my-character        # 系统生成，创建后不可改（见 §2.4）
name: 小岸                     # 显示名，可中文
title: 海边的朋友               # 一句话定位
description: 说话简短的朋友      # 简介（列表里展示）
tags: [朋友, 海边]
background: |                # 背景故事：常驻注入，排在人设正文之后
  小岸在海边长大，听得懂潮水的声音。
creator: user
prompt: |                    # 人设正文：支持 {{user_name}} 等状态变量宏
  你是{{user_name}}的朋友小岸，说话简短，不追问对方不想说的事。
variables: [user_name]        # 声明用到哪些状态变量（仅作记录与界面提示）
```

### 2.3 世界书条目 YAML

```yaml
id: user-night-talk
title: 深夜倾听模式
scope: "*"                   # "*" = 对所有角色生效；或填角色 id = 只对该角色生效
enabled: true
priority: 20                 # 注入排序权重（越大越靠前）
keys: [深夜, 失眠]            # 关键词：任一出现即触发（默认不区分大小写）
regex:                       # 正则：任一 search 命中即触发
  - 凌晨|睡不着
case_sensitive: false
vector_text: 用户表达入睡困难、夜里清醒这类困扰   # 语义触发文本（非空即启用向量通道）
vector_threshold: 0.7        # 语义命中阈值（**必须按当前 embedding 模型校准**）
content: |                   # 触发后注入的正文
  深夜时她会把台灯调暗、声音放轻，先陪着把今晚熬过去。
```

三个触发通道是**或**的关系：任一命中即触发。至少要有一个，否则写入被拒
（一条永远不触发的条目没有意义，还会让用户以为"写了却不生效"）。

### 2.4 id 规则（不可改）

角色 id 同时是**记忆隔离命名空间**：温层 Qdrant collection 名
（`memory_{companion_id}`）、冷层 companion 字段、个人记忆分库都用它。
因此：

- id 由系统生成，`user-` 前缀 + 标题的 ascii slug（中文标题回退 6 位随机后缀）；
- 格式限定 `^[a-z0-9][a-z0-9_-]{0,47}$`（同时满足 Qdrant collection 命名约束）；
- **创建后不可修改**——改 id 等于把角色换成一整套空记忆，界面只显示不提供编辑；
- **文风 id 同样自动生成且不可改**，但它**不承载任何持久语义**（记忆隔离用的是人设 id）：
  它只用来定位文件。id 分配看的是角色 / 条目 / 文风的**全集**，避免同名文件互相覆盖。

### 2.5 文风预设 YAML

```yaml
id: user-night-radio
name: 深夜电台
description: 低音量、慢节奏，像凌晨三点的电台
tags: [温柔, 慢, 留白]
style_prompt: |            # 正向风格指令（放 system 末尾，影响最强）——必填
  低声说话，句子短，一次只说一两句。
  先接住对方的情绪，再问一个具体的小问题。
avoid:                     # 少量必要禁令（只列最刺眼的 AI 腔，别写成长串负面清单）
  - 感叹号
  - 连续追问
examples:                  # 示例对话（2~3 组，反 AI 腔最有效的手段）
  - user: 我最近总是失眠
    assistant: 有几天了？
sampling:                  # 建议采样参数（可空；见下面的白名单）
  temperature: 0.8
  max_tokens: 200
conflicts_with: [聒噪, 长篇]  # 与人设冲突的特质关键词（只提示，不阻断）
```

**采样参数走白名单**（`app/studio/store.py` 的 `_SAMPLING_KEYS`）：
只认 `temperature`(0~2) / `max_tokens`(1~8192) / `top_p`(0~1) /
`frequency_penalty`(-2~2) / `presence_penalty`(-2~2)。键名或取值超出即 **400 拒绝**——
文风预设的 sampling **优先级最高**（会盖过模型预设档与酒馆预设作者的采样意图），
一个 `temperatur`（拼错）或 `temperature: 80` 不会被任何下游拦住，
只会让这份文风的每一轮对话都变得不可用，而用户完全看不出原因。

`examples` 里每组必须**同时**有 `user` 与 `assistant`：只有一边的「示例」
毫无示范价值。渲染时会在示例前加一句「示例中的人物与事件与用户本人无关」——
实测不加这句，模型会把示例里的具体内容当成用户的真实情况。

### 2.6 内置资源的编辑、删除与停用

内置资源在包目录（docker 镜像里可能只读），且是项目原创内容。它们不可直接修改，
但可以从当前创作工坊删除：删除只写用户目录的隐藏清单，**内置 YAML 一字未改**。

| 操作 | 内置角色 | 内置条目 | 我的内容 |
|---|---|---|---|
| 读取 / 展示 | ✅ | ✅ | ✅ |
| 直接修改 | ❌ 403 | ❌ 403 | ✅ |
| 从当前工坊删除 | ✅（写隐藏清单） | ✅（写隐藏清单） | ✅（删 YAML 文件） |
| 复制为我的 | ✅ | — | — |
| 启用 / 停用 | — | ✅（写用户侧偏好） | ✅（改本体） |

**「内置」包含外部来源**：插件数据源（如酒馆桥接）导入的角色同样按内置对待——
不能原地改（要改先「复制为我的」），但可以删除（写隐藏清单，不动来源文件）。

隐藏清单与停用偏好是同一套机制的三个文件，格式一致：

```json
{ "ids": ["energetic-roommate", "night-mode"] }
```

- 隐藏清单里出现某个内置 id → 该资源从**合并视图**（清单 / 详情 / 对话链路）里消失，
  再次 `GET /personas/{id}` 或 `GET /worldbook/{id}` 返回 404；
- 集合为空时文件会被直接删除，不留空壳；
- 文件损坏（非 JSON / 结构不符）按空集处理并记警告，不会让整个工坊打不开。

删除角色卡会**级联清理**它名下的会话、记忆与专属世界书条目（见 §4.3）；删除世界书条目则会让它不再出现在当前工坊与对话链路中。
内置资源没有界面恢复按钮，如需恢复可移除对应的用户侧隐藏清单条目。

**文风完全套用同一张表**：内置文风不可直接改（403），可以「复制为我的文风」，
也可以从当前工坊删除（写 `styles/deleted_builtin.json`）。
但**删除文风没有级联**——它不承载会话与记忆，删掉顶多让偏好里残留的 `style_id`
在下一轮回落默认档（`_resolve_style` 会给出「未知风格预设」告警）。

## 3. 接口

前缀 `/chat/studio`（`backend/app/api/studio.py`）。

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/catalog` | 一次性加载：角色清单 + 世界书条目 + 写作提示（变量名 / 字段上限） |
| GET | `/personas/{id}` | 角色详情（含人设正文；清单刻意不含正文） |
| POST | `/personas` | 新建角色 |
| PUT | `/personas/{id}` | 更新角色（未提交的字段不修改） |
| DELETE | `/personas/{id}` | 删除角色卡（内置 → 写隐藏清单）**并级联清理**会话 / 记忆 / 专属条目，见 §4.3 |
| POST | `/personas/{id}/duplicate` | 复制角色（内置 → 可编辑副本） |
| GET | `/worldbook/{id}` | 条目详情 |
| POST | `/worldbook` | 新建条目 |
| PUT | `/worldbook/{id}` | 更新条目 |
| DELETE | `/worldbook/{id}` | 删除条目（内置 → 写隐藏清单） |
| PATCH | `/worldbook/{id}/enabled` | 启用 / 停用 |
| POST | `/worldbook/test` | 试触发（草稿不落盘） |
| GET | `/styles/{id}` | 文风详情（含风格指令与示例；清单刻意不含正文） |
| POST | `/styles` | 新建文风 |
| PUT | `/styles/{id}` | 更新文风（未提交的字段不修改） |
| DELETE | `/styles/{id}` | 删除文风（内置 → 写隐藏清单；**无级联**） |
| POST | `/styles/{id}/duplicate` | 复制文风（内置 → 可编辑副本） |

`GET /catalog` 另外带回 `styles` 与 `sampling_spec`（采样参数的键名与取值区间）。
后者是刻意的：界面据此渲染输入框与即时校验，前端**不硬编码一份数字**——
两边漂移了用户看到的就是假提示。

约定：

- **每个写操作都会让对话图失效**（`invalidate_chat_graph()`），下一次对话按最新
  内容重建 —— 因此新角色/新条目/新文风「写完即生效」，不需要重启服务；
  文风清单本身也是**每次请求现取**（`app/api/chat.py` 的 `get_style_presets()`），
  不再像早期那样在模块导入时取一份快照——否则新建一份文风必须重启后端才看得见；
- 写操作响应里会带上**刷新后的 catalog**，前端不必二次拉取；
- 错误映射：参数非法 400、内置资源直接修改 403、不存在 404，`detail` 是可直接展示给用户
  的中文说明（例如「人设正文最多 8000 字，当前 9123 字」）。

### 3.1 试触发

`POST /worldbook/test` 用**草稿**（不落盘）判断一段样例文本是否命中，逐通道回报：

```json
{
  "matched": true,
  "keys_hit": ["猫"],
  "regex_hit": [],
  "vector_score": 0.83,
  "vector_threshold": 0.7,
  "scope": "*",
  "injected_text": "[小岸的猫]\n小岸养着一只叫「浪花」的白猫。",
  "estimated_tokens": 26,
  "warnings": []
}
```

只回一个 bool 是不够的：用户看到的永远是「没命中」却不知道为什么。因此这里把
**每个通道各自的结论**摊开（命中了哪些关键词、哪个正则、语义相似度与阈值的对比）。

草稿由 `StudioStore.build_draft_entry` 构造，**清洗与校验规则与写入路径完全一致**
（共用同一套代码），所以「试的时候命中、存下来却不命中」这类不一致不可能发生。
语义通道用的是**与对话链路同一个** embedding provider，否则两边的向量空间不同，
结论会互相矛盾。

## 4. 接入对话链路的语义

### 4.1 角色层

```
[角色人设] 人设正文
          [背景故事] 背景故事        ← 没有背景故事时不产生这一块
[世界书]   命中条目（按 priority + token 预算）
[个人记忆] …
```

人设层在 `PromptManager` 里是**必留层**（不参与裁剪），所以用户自撰内容有长度上限
（见 §4.4）——把一篇小说粘进人设正文会把上下文撑爆。

### 4.2 归属过滤

`worldbook_recall` 节点把当前 `companion_id` 传给匹配器，匹配器在**命中判定之前**
按 `entry.applies_to(companion_id)` 过滤：

- `scope="*"` → 对所有角色生效（与角色无关的通用条目用这个）；
- `scope=<角色 id>` → 只在该角色的会话里注入。内置条目按**内容归属**：写某个内置角色
  生活/设定的条目（苏澄的咨询室 / 团子 / 深夜模式）填该角色 id，这样用户换人设后
  不会看见别人的猫；写错了 id 的条目会永不触发（有测试卡住这一条）。

过滤放在命中判定之前而不是之后，是因为向量通道按 id 集合命中——放在后面会让专属
设定从向量通道漏给别的角色。匹配器的 `companion_id` 缺省为空串时**只匹配全局条目**
（刻意的 fail-safe：调用方忘了传宁可少注入，也不串味）。

### 4.3 删除角色卡 = 级联清理

删掉角色卡会**一并清掉**它名下的一切：

```
角色卡 → 专属世界书条目（scope = 该角色 id）
       → 该角色的全部会话（含消息留档）
       → 四层记忆（情景 / 事实 / 情绪日记 / 个人语料）
```

响应回报各层**实际删除的条数**（某层失败只记日志并计 0，不谎报成功）：

```json
{
  "deleted": "user-my-character",
  "name": "小岸",
  "removed_sessions": 3,
  "removed_turns": 12,
  "removed_entries": 1,
  "removed_memory": { "warm": 5, "facts": 4, "mood_log": 0, "knowledge": 2 }
}
```

内置角色同样级联；区别只在「删什么」——我的角色删 YAML 文件，
内置角色写隐藏清单（§2.6），两者的会话、记忆与专属条目都一并清除。

**为什么级联**：角色 id 是记忆隔离命名空间且创建后不可改（§2.4），卡片删掉后
这批会话与记忆再没有第二个角色能认领——留着既访问不到、又占着库。专属条目同理：
`scope` 指向已消失的角色，就成了永不触发的死条目（§4.2）。

**顺序**：先校验角色存在 → 删专属条目 → 删角色卡 → 删会话 → 清记忆。
先校验是必须的，否则会先删掉专属条目、再在角色上抛 404，
留下「条目没了、角色还在」的半截状态。

清理不可逆，界面因此必须做**二次确认**，并在删除后回报各层实际清除的条数（§6）。

> 只想清数据、留着角色卡：用控制台「会话与记忆」→「清空记忆」（`DELETE /chat/memory`）
> 或「清空会话」（`DELETE /chat/sessions`）。那两个入口各自只做一件事
> （前者清四层记忆但不动会话，后者只清会话），与「删角色」是三个不同的决定，
> 各自要有自己的二次确认。

### 4.4 写入校验（宁可报错也不写可疑数据）

| 检查 | 为什么 |
|---|---|
| 必填非空（角色名 / 人设正文 / 条目标题 / 条目正文） | 空角色对话起来毫无意义 |
| 至少一个触发条件 | 永不触发的条目会让人以为「写了却不生效」 |
| **正则必须可编译** | `matcher` 是直接 `re.search`——写坏一个括号会让**每一轮对话**都在召回阶段抛异常，而不是只让这一条不生效 |
| `scope` 指向的角色必须存在 | 指向幽灵角色的条目永远不会触发 |
| 字段长度上限 | 人设层是必留层，超长内容会撑爆上下文 |

上限（`backend/app/studio/store.py` 的 `LIMITS`，同时通过 `/catalog` 暴露给界面做
即时校验，避免前后端两套数字）：

| 字段 | 上限 |
|---|---|
| 角色名 / 一句话定位 / 简介 | 50 / 100 / 500 字 |
| 人设正文 / 背景故事 | 各 8000 字 |
| 标签 / 状态变量名 | 各 20 / 40 条，单项 30 / 40 字 |
| 条目标题 / 正文 / 语义触发文本 | 100 / 4000 / 500 字 |
| 关键词 / 正则 | 各 50 条，单项 100 字 |

### 4.5 读接口对坏文件宽容

用户手改 YAML 是常态。单个文件写坏（语法错、文件内 id 与文件名不一致）只会被
**跳过并记入警告**，不影响其它内容；警告通过 catalog 返回给界面显示——

```json
{ "warnings": ["角色文件 user-broken.yaml 解析失败，已跳过：…"] }
```

反过来，写接口一律严进（上表），绝不写入可疑数据。读宽写严是有意的取舍：
读侧宽容能保证「一个坏文件不会让所有角色都用不了」，写侧严格能保证「存下去的一定是
能用的」。

## 5. 合规

（AGENTS.md §6 的落地）

| 类别 | 处理 |
|---|---|
| **发行内容**（源码 / 内置角色与世界书 / 文档） | 全部自写，无第三方提示词原文 |
| **用户自撰内容** | 只落 `backend/data/studio/`（已 gitignore），**不进仓库、不随发行物分发** |
| **与 SillyTavern 的关系** | 只借鉴机制思想（条目触发 + 注入分档 + 用户侧编辑），代码与提示词 100% 原创 |

内置条目允许被「停用」或「删除」但不允许被改写，也是同一原则的延伸：**用户对内置内容
的所有偏好（停用 / 隐藏）都写在用户侧文件里**，发行物永不被运行期行为污染。

## 6. 前端交互（创作工坊面板）

入口在页面顶栏「创作工坊」，面板内含三个分区（我的角色 / 世界书 / 文风，文风见本节末）：

- **我的角色**：左侧列表（内置带徽标）+ 右侧表单（角色名 / 定位 / 简介 / 标签 /
  人设正文 / 背景故事）。内置角色表单置灰（不可直接改），保留「复制为我的角色」与
  「删除角色卡」两个动作；点击状态变量提示按钮可把 `{{user_name}}` 之类插到正文
  末尾；字数实时对照上限。
- **世界书**：左侧条目列表（归属徽标 / 已停用徽标 / 启停开关）+ 右侧表单
  （标题 / 归属下拉 / 关键词 / 正则 / 语义文本与阈值 / 优先级 / 正文）+
  **试触发**区（输入一句样例，逐通道显示结论与将要注入的文本）。内置条目同样可删除。

删除是**两步确认**（点「删除」→ 二次确认后才提交）；确认文案明确说明
「该角色的全部会话、记忆与专属世界书条目都会一并清除，不可恢复」，内置资源还要
额外说明「只写用户侧隐藏清单、不改包内文件」。删除后回报各层实际清除的条数，
用户才知道到底清掉了什么。

新建条目的默认归属是**当前对话角色**，这样给专属角色写设定时不必每次手动选一遍。
对话进行中（`session.busy`）面板整体禁用，避免与正在跑的对话争用配置。

面板分三个分区（`persona` / `worldbook` / `style`）：

- **我的角色**：列表 + 表单（角色名 / 定位 / 简介 / 标签 / 状态变量 / 人设正文 / 背景故事），
  以及「AI 补全」——用一句话让模型先写一版草稿，**只填表单不落盘**；
- **世界书**：条目编辑 + 「试触发」逐通道结论；
- **文风**：风格指令 / 避免表达 / 标签 / 冲突特质 / **示例对话**（可增删的成对输入，
  而不是一段自由文本，免得用户写成模型读不懂的格式）/ **采样参数**（键名与区间来自
  `catalog.sampling_spec`）。文风写入后页面会顺带刷新 `GET /chat/styles`，
  新建的文风立刻出现在文风选择器里。
